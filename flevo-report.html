الأمان

مشكلات تتطلب معالجة فورية

مفتاح Supabase مكشوف في ملف عام

حرج

الملف assets/supabase-config.js يحتوي على URL وKey مكشوفَين بالكامل في الكود المصدري. رغم أن Supabase يسميه "publishable key"، إلا أن أي شخص يمكنه فحص source code استخدامه مباشرةً للاستعلام عن قاعدة البيانات — خاصةً إذا كانت سياسات RLS غير محكمة.

window.FLEVO_SUPABASE_KEY = 'sb_publishable_aGQVei7szUD6ChwedNo3hQ_WPSQw9o3';
التوصية: تحقق أن Row Level Security (RLS) مفعَّل على جميع الجداول في Supabase. جداول quotation_requests وservices يجب أن تسمح بالكتابة للزوار فقط، وقراءة الكل وحذفه مقصورة على المصادق عليهم. هذا يجعل كشف المفتاح مقبولاً — لكن RLS الصارم هو ضمانة لا خيار.

غياب Content Security Policy (CSP)

حرج

لا يوجد أي header أو meta tag لـ CSP في أي من صفحات الموقع. هذا يعرض الموقع لهجمات XSS والحقن. الموقع يحمل محتوى ديناميكياً من Supabase ويضعه في innerHTML مما يجعل هذا الغياب أكثر خطورة.

التوصية: أضف header على مستوى الـ server: Content-Security-Policy: default-src 'self'; script-src 'self' cdn.jsdelivr.net cdnjs.cloudflare.com; font-src fonts.gstatic.com; connect-src *.supabase.co

حماية صفحات الإدارة معتمدة على JavaScript فقط

عالي

صفحات admin.html وdashboard.html وquotes.html مُقيَّدة بـ data-flevo-protected="true" وكود JS يفتح نافذة تسجيل الدخول. لكن HTML الصفحة كاملاً يُحمَّل في المتصفح قبل التحقق. مشغل JS المعطوب أو مستخدم متقدم يمكنه رؤية هيكل الصفحة.

التوصية: الحماية الحقيقية تكون على مستوى Supabase RLS. الكود الحالي كافٍ UX-wise، لكن تأكد أن كل endpoint في Supabase يتحقق من الجلسة وليس فقط الـ frontend.

الأداء

عوامل تبطئ التحميل وتؤثر على Core Web Vitals

12 ملف CSS محمَّل في كل صفحة

أعلى أولوية

الصفحة الرئيسية تحمل 12 طلب CSS منفصل (site.css، final-theme.css، pixel-perfect-theme.css، layout-fixes.css، navigation-fixes.css، quote.css، motion.css، unified-auth.css، flevo-header-v512.css، qr-contact-profile.css، home-projects-carousel.css، testimonials-carousel.css، articles-section.css). كل طلب هو round-trip إضافي يؤخر الـ First Contentful Paint. ملاحظة: هذه الملفات تكشف عن تاريخ التطوير التراكمي — patches فوق patches.

الحل: دمج الـ CSS في ملفَّين: critical.css (ما يُرسم فوق الطية) و app.css (الباقي). يمكن استخدام أداة بسيطة مثل esbuild أو Vite أو حتى script cat بسيط في build pipeline.

Google Fonts تعيق الـ render

عالي

الصفحة تحمل Cairo وMontserrat من fonts.googleapis.com بشكل blocking. في الشبكات البطيئة أو عند إخفاق CDN، لا يُعرَض أي نص حتى تحمل الخطوط (FOIT). لا يوجد font-display: swap.

الحل: أضف display=swap للرابط: fonts.googleapis.com/css2?...&display=swap — أو الأفضل: حمِّل الخطوط self-hosted بـ @font-face مع font-display: swap لضمان عدم الاعتماد على CDN خارجي.

صورة Hero غير مُحمَّلة مسبقاً (LCP)

عالي

صورة الـ Hero هي CSS background-image للـ .hero section — المتصفح لا يكتشفها إلا بعد تنزيل CSS وتطبيقه. هذا يؤثر مباشرةً على مؤشر LCP (Largest Contentful Paint) في Google Core Web Vitals، وهو عامل ترتيب في محركات البحث.

<link rel="preload" as="image" href="assets/images/hero.webp">
الحل: أضف link rel="preload" لصورة الـ Hero في <head>. لكن الأفضل على المدى البعيد: استخدم <img> مع object-fit: cover داخل .hero بدل background-image لتسريع اكتشاف المتصفح لها.

لا يوجد Service Worker للـ PWA

متوسط

manifest.webmanifest موجود لكن لا يوجد service worker. الموقع يُعلن عن نفسه كـ PWA لكن لا يعمل offline ولا يُخزَّن cache. بدون service worker، التثبيت على الجهاز لا يضيف قيمة حقيقية.

الحل: أضف service worker بسيط يُخزِّن HTML وCSS وJS الأساسيين (Cache-First للأصول الثابتة، Network-First للـ Supabase calls). مكتبة Workbox تُبسِّط هذا كثيراً.

لا يوجد cache-busting للأصول

متوسط

ملفات CSS وJS تُحمَّل بأسماء ثابتة (site.css، quote.js). عند تحديث الموقع، المتصفحات قد تستخدم نسخ قديمة مخزَّنة حتى انتهاء صلاحية الـ cache. هذا يسبب تجربة مستخدم مربكة بعد التحديثات.

الحل: أضف query string بـ version hash عند البناء: site.css?v=1.2.3 أو استخدم content-hash في اسم الملف: site.abc123.css — هذا يتطلب إضافة خطوة build بسيطة.

تحسين محركات البحث (SEO)

المشكلات التي تحرم الموقع من ظهور أفضل في جوجل

غياب تام لبيانات Open Graph وTwitter Cards

حرج

لا يوجد أي meta tag من نوع og:title أو og:description أو og:image في أي صفحة. عند مشاركة الموقع على LinkedIn أو Facebook أو WhatsApp أو X، تظهر بطاقة مشاركة فارغة بلا صورة ولا وصف — وهو ضعف تسويقي مباشر لشركة تبني تجارب بصرية.

<meta property="og:title" content="FLEVO Creative Industries | بوثات ومعارض"> <meta property="og:description" content="نصمم ونصنع وننفّذ البوثات والمعارض..."> <meta property="og:image" content="https://flevo.com/assets/hero-flevo-final.webp"> <meta property="og:type" content="website"> <meta name="twitter:card" content="summary_large_image">

غياب البيانات الهيكلية (JSON-LD)

حرج

لا يوجد أي Schema.org markup. جوجل لا يعرف أن الموقع لـ LocalBusiness — مما يحرمه من ظهور نتيجة غنية (Rich Result) في نتائج البحث مع رقم الهاتف والموقع والتقييم وساعات العمل.

<script type="application/ld+json"> { "@context": "https://schema.org", "@type": "LocalBusiness", "name": "FLEVO Creative Industries", "telephone": "+201004478632", "address": { "@type": "PostalAddress", "addressLocality": "6 أكتوبر", "addressCountry": "EG" }, "url": "https://www.flevo.com" } </script>

وصفان meta description متكرران في index.html

خطأ تقني

ملف index.html يحتوي على وسمَي meta description (سطر 9 والسطر 31). جوجل يتجاهل الوصفَين ويكتب وصفه الخاص — مما يُضيع جهد صياغة الوصف التسويقي.

<meta content="فليفو للصناعات الإبداعية..." name="description"/> <meta content="FLEVO Creative Industries - ..." name="description"/>
الحل: احتفظ بوصف واحد عربي محسَّن يحتوي على الكلمات المفتاحية الأساسية (بوث معرض، تصنيع، مصر)، وأزل الوصف المكرر.

H1 يكرر نص الـ eyebrow بالكامل

عالي

في قسم الـ Hero، نص الـ eyebrow div هو "نحو تجربة تُلهم" وأول كلمات الـ H1 هي أيضاً "نحو تجربة تُلهم". جوجل يرى هذا كـ H1 مكرر مع محتوى قبله، وتضعف قيمة الكلمات المفتاحية في الـ H1.

الحل: غيّر نص الـ eyebrow لشيء مختلف — مثلاً: "شريكك الاستراتيجي في المعارض والفعاليات" — واحتفظ بالـ H1 للكلمات المفتاحية الرئيسية.

sitemap.xml ناقص ولا يحتوي على صفحات المقالات والمشروعات

عالي

sitemap.xml يحتوي على 4 URLs فقط (index، projects، gallery، profile). مفقودة: articles.html وصفحات article.html الديناميكية وصفحات project.html — وهي المحتوى الأكثر قيمة لـ SEO لأنها تحتوي على نصوص تفصيلية.

الحل: أضف articles.html للـ sitemap يدوياً، ثم اعمل على توليد ديناميكي لـ sitemap يجلب slugs المشروعات والمقالات من Supabase ويُولِّد sitemap.xml تلقائياً عند البناء.

لا يوجد canonical tags

متوسط

بدون <link rel="canonical"> في كل صفحة، جوجل قد يرى نسخ متعددة من نفس الصفحة (http/https، www/non-www، مع/بدون trailing slash) كمحتوى مكرر ويُضعف ترتيبها.

جودة الكود والبنية التقنية

الديون التقنية التي تصعّب الصيانة والتطوير مستقبلاً

تراكم ملفات CSS التصحيحية (Patch Files)

دَين تقني

بدلاً من تعديل الـ CSS الأصلي، تراكمت ملفات تصحيح: layout-fixes.css، navigation-fixes.css، pixel-perfect-theme.css، final-theme.css. هذا يجعل تتبع من أين تأتي قيمة CSS معينة شبه مستحيل، ويُصعِّب أي تعديل مستقبلي.

الحل المقترح: خصِّص sprint واحد لإعادة هيكلة CSS: ادمج كل الـ patches في ملف واحد منظم، وأزل التكرار. ابدأ بـ "نظام tokens" بسيط (custom properties) ثم ابنِ Components فوقه.

تعارض breakpoints بين ملفات CSS

تعارض

الـ Header CSS (flevo-header-v512.css) يستخدم max-width: 1040px كنقطة كسر للـ mobile. لكن index.html الأصلي وملفات أخرى تستخدم max-width: 980px. هذا يعني وجود منطقة رمادية (980-1040px) تتضارب فيها قواعد CSS.

الحل: اختر نقطة كسر واحدة: 1040px للـ tablet/desktop وطبِّقها في كل الملفات. أضف CSS custom property: --bp-mobile: 1040px كمرجع موحَّد.

ملفَّان يتنافسان على التحكم في القائمة المتنقلة

تعارض

كلٌّ من flevo-header-v512.js وnavigation-audit.js يحتويان على كود لفتح/إغلاق القائمة المتنقلة. flevo-header-v512.js يتحقق if(!toggle.dataset.flevoBound) كـ failsafe، لكن هذا الأسلوب هش ويخفي وجود تعارض بدلاً من حله.

الحل: اجعل navigation-audit.js المرجع الوحيد للـ mobile menu. احذف كود القائمة من flevo-header-v512.js أو العكس — لا تحتاج لكليهما.

نظام i18n يمشي الـ DOM كاملاً عند تغيير اللغة

أداء

دالة apply() في i18n.js تُنفِّذ document.querySelectorAll('body *:not(script):not(style)') وتمر على كل عقدة نصية في الصفحة. على الصفحات الكبيرة (مثل projects.html مع 350+ مشروع)، هذا يعني توقف واضح عند تغيير اللغة.

الحل: استخدم نظام data attributes: ضع النص العربي في data-ar والإنجليزي في data-en على كل عنصر، وغيِّر textContent فقط للعناصر التي تحمل هذه السمات بدلاً من كل عناصر الصفحة.

المقالات بيانات ثابتة (JS file) بدلاً من Supabase

تناقض معماري

بينما المشروعات والخدمات والاقتباسات والإعدادات تأتي من Supabase ديناميكياً، المقالات لا تزال محددة يدوياً في assets/articles-data.js. هذا يعني أن إضافة مقالة جديدة تتطلب تعديل كود JS وإعادة نشر الملف.

الحل: أنشئ جدول articles في Supabase مع الحقول الحالية (title_ar، title_en، excerpt، date، image)، وأضف صفحة إدارة للمقالات مشابهة لصفحة admin.html للمشروعات.

data/projects.json غير مستخدم

ملف بائت

يوجد ملف data/projects.json يحتوي على 6 مشروعات، لكن الكود الحالي يجلب كل البيانات من Supabase. هذا الملف أثر متبقي من نسخة أقدم وقد يُسبِّب ارتباكاً للمطورين في المستقبل.

الحل: احذف الملف من المستودع بعد التحقق أنه غير مستخدم في أي مكان.

تجربة المستخدم وإمكانية الوصول

مشكلات تؤثر على المستخدم مباشرةً

روابط التواصل الاجتماعي فارغة تماماً

مكسور

في الـ footer، روابط التواصل الاجتماعي هي <a>f</a> و<a>◎</a> و<a>in</a> و<a>▶</a> — بدون href على الإطلاق. النقر عليها لا يفعل شيئاً. هذا يسبب ارتباكاً للزوار وهو محرج مع شركة تعتمد على التسويق الرقمي.

الحل الفوري: أضف روابط حقيقية لـ Facebook وInstagram وLinkedIn وYouTube، أو أخفِ هذا القسم إذا لم تكن هناك حسابات رسمية حالياً. لا شيء أسوأ من وهم الحضور الرقمي.

زر تشغيل وهمي على صورة ثابتة (Why FLEVO)

مضلل

قسم "لماذا FLEVO؟" يعرض صورة مشروع مع زر تشغيل دائري (▶ مُضاف بـ CSS ::after pseudo-element). لكن النقر عليه لا يفتح أي فيديو — الصورة ثابتة تماماً. هذا يخلق توقعاً زائفاً لدى الزائر ويُضر بمصداقية الموقع.

الحل: إما أزل pseudo-element الزر (احذف .video-card::after من CSS)، وإما أضف فيديو حقيقي من YouTube أو Supabase Storage يُفتح عند النقر في iframe أو modal.

manifest.webmanifest: أيقونة واحدة ونوع غير صحيح

PWA

الـ manifest يحتوي على أيقونة PNG واحدة (512×512) فقط. الـ PWA يحتاج عدة أحجام (192×192 كحد أدنى) وأيقونة maskable للأجهزة الحديثة. كما أن الأيقونة الحالية ليست وضوح مثالي لشاشات الـ iOS.

الحل: أضف أيقونتين على الأقل: 192×192 (icon-192.png) و512×512 (icon-512.png) مع نوع "maskable" للأيقونة الكبيرة.

لا يوجد نموذج تواصل نصي

فجوة

قسم التواصل يعتمد كلياً على WhatsApp والاتصال الهاتفي. العملاء الذين يفضلون التواصل عبر البريد الإلكتروني أو النموذج المكتوب (خاصةً العملاء الدوليين) لا يجدون خياراً. نموذج عرض السعر موجود لكنه للعملاء الجاهزين للشراء فقط.

الحل: أضف نموذج "اسألنا" بسيط (الاسم، الإيميل، الرسالة) يُحفَظ في Supabase جدول contact_messages — يمكن إعادة استخدام نفس بنية quotation_requests مع تبسيط الحقول.

تحسينات SEO والأداء — تأثير مباشر على الظهور

2–3 أسابيع
  • Open Graph + Twitter Cards: أضفهم في كل صفحة — أكبر تحسين تسويقي بأقل جهد.
  • JSON-LD LocalBusiness: أضف بيانات هيكلية لتحقيق Rich Results في جوجل.
  • Canonical tags: أضف <link rel="canonical"> في كل صفحة.

  • Preload لصورة Hero: أضف <link rel="preload"> لتحسين LCP.
  • CSP headers: أضف Content-Security-Policy عبر server config.

  • دمج CSS: اجمع الـ 12 ملف في ملفَّين: critical.css وapp.css — أكبر تحسين أداء ممكن.
  • توحيد breakpoints: اختر 1040px كنقطة كسر وحيدة للـ mobile في جميع الملفات.
  • توحيد mobile menu: اجعل ملف JS واحد مسؤولاً عن القائمة المتنقلة.
  • تحسين i18n: استبدل DOM-walk بـ data-ar/data-en attributes.
  • Cache-busting: أضف version hash لأسماء ملفات CSS/JS.
٤

  • نقل المقالات لـ Supabase: أنشئ جدول articles وصفحة إدارة لها للتحرر من تعديل الكود لكل مقال.
  • Service Worker: فعِّل التخزين المؤقت لتحقيق PWA حقيقي يعمل offline.
  • نموذج تواصل نصي: أضف نموذجاً بسيطاً للعملاء الذين لا يريدون الاتصال الفوري.
  • PWA icons: أضف أيقونات بأحجام متعددة مع نوع maskable للدعم الكامل.
  • Build pipeline: أضف Vite أو esbuild لأتمتة الـ bundle والـ cache-busting في خطوة واحدة.
